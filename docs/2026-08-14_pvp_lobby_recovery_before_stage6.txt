HALLVALLA - RECUPERACION PVP / LOBBY ANTES DE ETAPA 6
Fecha: 14 de agosto de 2026
Base: Hallvalla.zip entregado desde la carpeta GitHub del usuario

SINTOMA REPORTADO
Al pulsar "Crear partida" el botón queda bloqueado con el tooltip "Operación PvP en curso...",
la sala no se abre y la página puede quedar sin una salida útil para diagnosticar el fallo.

HALLAZGO DE CONTINUIDAD
El código runtime del ZIP entregado coincide con la Etapa 5 entregada anteriormente; no aparece
un documento de Etapa 6 dentro de la base. Por tanto esta reparación no avanza la Etapa 6: primero
restaura/fortalece la entrada PvP sobre la base real subida por el usuario.

DIAGNOSTICO ESTATICO
1. El texto "Operación PvP en curso..." se activa cuando beginPvpLobbyOperation() fija el lock local.
2. Ese lock solo se libera cuando la operación asíncrona termina o entra en finally.
3. Desde Etapa 4, createGame() reservaba el código ejecutando runTransaction() directamente sobre
   games/{code}/public y devolviendo dentro de la transacción TODO el estado público inicial.
4. La prueba práctica reportada es el primer dato dinámico que demuestra que esa ruta puede quedar
   pendiente en el entorno real del usuario.
5. Adicionalmente, las Etapas 3/4/5 conservaron el mismo CACHE_BUILD/query string, de modo que un
   despliegue sobre GitHub Pages podía reutilizar módulos JS cacheados de una entrega anterior.

REPARACION APLICADA
1. Claim pequeño y separado para el código de sala
   - El claim atómico ya NO escribe el objeto public completo dentro de runTransaction().
   - Se reserva únicamente games/{code}/roomClaim = uid mediante una transacción pequeña.
   - Tras confirmar el claim se comprueba que games/{code}/public no exista.
   - Solo entonces se crea public mediante set().
   - Se usan códigos PvP de 8 caracteres; el input ya admitía hasta 8.
   - Las salas legacy sin roomClaim nunca se sobrescriben: si public ya existe se libera el claim
     y se genera otro código.

2. Watchdog de Firebase en lobby
   - Crear/Unirse tienen límite de espera de 12 segundos para las operaciones críticas.
   - Si Firebase no responde, el lock local se libera y se muestra un aviso visible sin requerir DevTools.
   - Para una transacción que confirmara tarde se instala cleanup de la reserva huérfana.
   - Rollbacks/liberaciones también tienen límite de espera para no dejar la interfaz bloqueada.

3. Progreso visible
   - Crear informa cuando la sala ya fue reservada y está preparando private/player1.
   - Unirse informa cuando J2 fue reservado y está preparando private/player2.
   - Permission denied y timeout muestran hvAlert visible, además de lobbyStatus.

4. Cache busting real para GitHub Pages
   - BUILD actualizado con sufijo PVPRECOVERY1.
   - CACHE_BUILD actualizado con sufijo 20260814A.
   - index.html, styles.css query, bootstrap-loader query, imports de firebase-config y módulos usan
     un identificador nuevo para impedir mezclar JS viejo y nuevo en el navegador.

FIREBASE RULES - CAMBIO OBLIGATORIO
Se agregó games/$gameId/roomClaim con permisos autenticados de lectura y claim/release exclusivo
por UID. Copiar/publicar database.rules.json de esta versión en Firebase Realtime Database > Rules.
Este cambio NO se aplica automáticamente al copiar el ZIP a GitHub.

PRUEBA PRACTICA RECOMENDADA
1. Publicar primero database.rules.json de esta versión en Firebase.
2. Sobrescribir el proyecto en GitHub con esta versión.
3. Esperar a que GitHub Pages termine de desplegar y hacer recarga dura una vez.
4. Pulsar Crear partida.
   - Debe pasar de "Reservando una sala segura..." a "Sala XXXXXXXX reservada..." y abrir el lobby.
   - Si Firebase no responde en 12 s, debe aparecer un modal de timeout y los botones deben volver
     a habilitarse en vez de quedar bloqueados indefinidamente.
5. Desde un segundo cliente, introducir el código de 8 caracteres y probar Unirse.
