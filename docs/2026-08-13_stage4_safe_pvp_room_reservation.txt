HALLVALLA - ETAPA 4 / RESERVA SEGURA DE SALAS Y JUGADOR 2
Fecha: 13 de agosto de 2026
Base de trabajo: Hallvalla_STAGE3_PVP_LIFECYCLE_REGISTRY.zip

CONTEXTO
La validación dinámica de la Etapa 3 queda diferida porque en este momento no es posible
probar el PvP con dos clientes. La Etapa 4 se implementa sobre la Etapa 3 sin declarar
cerradas las pruebas dinámicas pendientes de la etapa anterior.

OBJETIVO DE ESTA ETAPA
Eliminar carreras de creación/unión del lobby PvP:
- una sala nueva no debe sobrescribir accidentalmente otra sala existente;
- dos jugadores distintos no deben poder reclamar simultáneamente el puesto J2;
- abandonar/cancelar una operación de creación/unión no debe dejar una reserva huérfana;
- salir del lobby como J2 debe liberar de forma consistente el slot y su estado privado.

SITUACION ENCONTRADA AL INICIAR
La base de Etapa 3 ya heredaba de Etapa 2 un runTransaction() para reclamar
public/playerSlots/player2Uid. Esa parte se conservó y se reforzó. La creación de salas,
en cambio, todavía usaba code4() + set(public), por lo que el código no tenía un claim
atómico y seguía existiendo el riesgo de colisión/sobrescritura indicado en la auditoría.

IMPLEMENTACION REALIZADA
1. Códigos PvP de 6 caracteres
   - Se agregó makePvpRoomCode() usando un alfabeto base32 sin I/O/0/1 ambiguos.
   - Usa crypto.getRandomValues() cuando está disponible y Math.random() solo como fallback.
   - Los códigos de Aventura/Tutorial/LOCAL conservan code4(); el cambio se limita a salas PvP.
   - joinGame() normaliza entradas y sigue aceptando códigos antiguos de 4 caracteres.

2. Claim atómico del código de sala
   - createGame() ya no hace set() directo sobre games/{code}/public.
   - reserveNewPvpPublicRoom() usa runTransaction() en games/{code}/public.
   - Solo crea la sala si public no existe; si existe, la transacción aborta y genera otro código.
   - Se permiten hasta 12 intentos antes de devolver un error explícito.
   - La sala pública se reserva antes de escribir private/player1.

3. Prevención de doble operación local
   - Crear/Unirse comparten un lock de operación PvP por cliente.
   - Mientras una creación/unión está en curso, ambos botones quedan deshabilitados.
   - Volver al menú/cerrar el lobby invalida la operación pendiente.
   - Cada await crítico comprueba que la operación siga activa antes de continuar.

4. Rollback de creación
   - Si una creación reserva public pero falla/cancela antes de completar private/player1,
     rollbackCreatedPvpRoom() revierte mediante transacción.
   - Si J2 alcanzó a entrar mientras J1 cancela, la sala se marca abandoned en lugar de borrar
     el estado debajo de un segundo cliente.

5. Claim J2 conservado y endurecido
   - J2 continúa reclamando playerSlots/player2Uid mediante runTransaction().
   - Un UID diferente no puede sustituir al UID que ganó la reserva desde el runtime normal.
   - Después del claim se vuelve a leer public y se exige phase === waiting y ownership J2 válido.
   - Antes de preparar una reentrada se retiran de la copia de trabajo Principales antiguos de J2,
     evitando duplicarlos si el mismo UID vuelve a intentar entrar.

6. Orden seguro de preparación J2
   - Tras ganar el slot, se escribe primero private/player2.
   - Solo después se publica nombre/líder/Principales/stats/unidades de J2 en public.
   - Si falla o se cancela la preparación, resetPvpPlayer2Reservation() intenta devolver la sala
     al estado sin rival mediante una transacción sobre public.

7. Salida J2 transaccional
   - SALIR ya no limpia player2Uid mediante un update independiente.
   - La liberación del slot y el saneamiento del estado público de J2 se realizan dentro de una
     transacción condicionada a que el slot todavía pertenezca al UID que sale.
   - Se eliminan Principales no-líder de J2 para que el siguiente rival no herede tokens viejos.

8. Reglas Firebase privadas actualizadas
   - private/player1 y private/player2 pueden eliminarse por su ownerUid al abandonar.
   - El propietario actual del slot público puede escribir/reemplazar su rama privada, incluso si
     quedó una rama privada antigua de una versión previa.
   - Esto evita que un private/player2 obsoleto bloquee para siempre a un nuevo J2 tras una salida.

VALIDACION ESTATICA EJECUTADA
- 21/21 archivos JavaScript pasan node --check.
- 5/5 archivos JSON parsean correctamente.
- createGame() ya no llama code4() para el código PvP.
- No existe private/player-IA en código runtime.
- La creación PvP usa reserva transaccional del nodo public.
- J2 conserva exactamente un claim runTransaction() sobre playerSlots/player2Uid.
- Prueba aislada de lógica transaccional:
    * primer UID reclama J2;
    * segundo UID no lo sustituye;
    * el mismo UID es idempotente;
    * una sala vacía puede reservarse;
    * una sala existente no se sobrescribe.

VALIDACION DINAMICA PENDIENTE
No se declara verificada en Firebase real porque actualmente no es posible probar PvP.
Cuando vuelva a estar disponible la prueba con dos clientes, ejecutar:

1. Crear muchas salas seguidas y confirmar códigos de 6 caracteres y cero sobrescrituras.
2. Lanzar dos intentos J2 casi simultáneos desde clientes con UID distintos: solo uno entra.
3. Cancelar/volver al menú durante Crear y durante Unirse: no debe quedar slot huérfano.
4. J2 entra -> sale -> entra un J2 diferente: private/player2 debe aceptar al nuevo owner.
5. J2 entra -> sale -> J2 nuevo entra: no deben reaparecer Principales/tokens del rival anterior.
6. Crear -> J2 entra -> J1 abandona durante espera: ambos clientes deben ver sala abandonada.
7. Repetir con red interrumpida durante claim/prepare y revisar el estado Firebase final.
