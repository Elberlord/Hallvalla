HALLVALLA - ETAPA 3 / LIFECYCLE PVP COMPLETO
Fecha: 13 de agosto de 2026
Base de trabajo: Hallvalla_STAGE2_PVP_LOBBY_RECOVERED_TUNER_V3.zip

OBJETIVO DE ESTA ETAPA
Centralizar el ownership de recursos efimeros de lobby/batalla para que listeners,
timers, requestAnimationFrame, observers, FX/audio y callbacks temporales no
sobrevivan al salir de una partida, cambiar de sala o entrar en una batalla nueva.
Esta etapa NO cambia reglas de juego, balance, cartas, CSS ni assets.

IMPLEMENTACION REALIZADA
1. Registro central de disposables
   - Se agrego createHallvallaDisposableRegistry() en 03-runtime-clocks.js.
   - Existen dos scopes independientes:
       * battle
       * pvp-lobby
   - Cada scope usa una generacion/token para invalidar callbacks de una sesion anterior.
   - Puede poseer y limpiar: Firebase unsubscribe, timeouts, intervals, RAF,
     event listeners, observers, nodos temporales, delays cancelables y SFX.

2. Lifecycle de lobby PvP
   - openPvpLobbyRoom() inicia un scope pvp-lobby.
   - clearPvpLobbyRoomState() destruye el scope.
   - El onValue del lobby queda registrado como disposable.
   - Los callbacks de Firebase comprueban el token de lifecycle antes de tocar UI/estado.

3. Lifecycle de batalla
   - enterGame() y enterLocalGame() inician una nueva generacion battle.
   - resetBattleState() destruye la generacion battle antes de limpiar estado global.
   - Al reemplazar una batalla, la generacion anterior se invalida y sus recursos
     quedan cancelados antes de instalar los nuevos.
   - El loop del reloj se fuerza a reiniciar para evitar conservar un ID de interval
     perteneciente a una generacion ya destruida.

4. Suscripciones Firebase de batalla
   - public/onValue y private/onValue quedan registrados como disposables battle.
   - Ambos listeners comprueban el token capturado al entrar en la batalla.
   - updatePublic() y updatePrivate() fijan gameId/player/token al comenzar la operacion
     y abortan si la sesion cambia mientras existe un await. Esto evita que una accion
     iniciada en una batalla termine escribiendo sobre otra batalla recien abierta.
   - Esto NO convierte las jugadas en atomicas; la atomicidad sigue reservada para
     la Etapa 5.

5. Timers, RAF y FX
   - Reloj de turno, watchdog IA, disparadores IA, anuncios de fase, seleccion visual,
     recarga de recurso, auto-avances, outcome splash y timers de FX usan el registro.
   - Los requestAnimationFrame de FX y overlays de batalla quedan cancelables por lifecycle.
   - Los intervals temporales de FX quedan registrados y se destruyen al salir.
   - Los SFX de una batalla se registran mientras estan reproduciendose y se liberan
     al terminar; si se abandona la batalla antes, se detienen durante el cleanup.

6. Listeners/observers de UI creados durante batalla
   - El drag del tablero registra pointermove/pointerup/pointercancel de window y los
     elimina tanto al terminar el drag como al abandonar la batalla.
   - El estado de drag se limpia al reset/reentrada.
   - El layer de lideres se vuelve propiedad del lifecycle de batalla.
   - Los listeners resize/orientationchange de proxies de lideres quedan registrados.
   - El ResizeObserver de retrato DET queda registrado y desconectable.

7. Callbacks IA / Aventura que podian sobrevivir a una sesion
   - adventureEnemyTurn() fija gameId + token de lifecycle.
   - Sus delays pasan a battleSleep() cancelable.
   - Cada publicacion importante verifica que la batalla original siga activa.
   - La recuperacion de maybeTriggerAdventureAI() usa el gameId capturado y no puede
     recuperar accidentalmente un turno dentro de una batalla nueva.
   - Dragon Contract aplica el mismo guard al delay y a sus escrituras de turno.

8. Nodos temporales especiales
   - El selector de orden de Salomon queda asociado al lifecycle battle para que el
     overlay pueda retirarse si se abandona la batalla antes de terminar la seleccion.

DEBUG / INSTRUMENTACION
En consola del navegador:

  __HALLVALLA_LIFECYCLE_SNAPSHOT__()

Devuelve los scopes battle y pvpLobby con:
- active
- generation
- resourceCount
- byKind
- resources (kind + label)
- meta
- lastDisposeReason

Despues de salir completamente de una batalla se espera:
  battle.active === false
  battle.resourceCount === 0

Despues de cerrar/abandonar un lobby se espera:
  pvpLobby.active === false
  pvpLobby.resourceCount === 0
