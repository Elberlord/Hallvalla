HALLVALLA — CONTRATOS DE VENTANA DEL MOTOR CONTINUO
Documento técnico interno de compatibilidad
Base revisada: v240 · 2026-09-20

IMPORTANTE — VISIBILIDAD
HallValla ya no usa un modelo de turnos de jugador. La interfaz de producción no debe
mostrar TR, RTC, turnKey, turnPhase, combatWindowKey ni runtimeMode. Para el jugador
existe simplemente el combate normal.

1. CONTRATO CANÓNICO ACTIVO

El código de gameplay v240 usa:

    combatWindowKey
    combatWindowIndex
    combatWindowStartedAt
    runtimeMode
    *WindowKey
    *UsedWindow
    damagedThisWindow
    cyclesRemaining

`runtimeMode` puede ser `prebattle` o `continuous`. No representa Draw/Main/End Phase.
`combatWindowKey` identifica una ventana periódica técnica del motor y sirve para
expiración, activación única, limpieza y deduplicación. Nunca determina qué jugador
puede actuar.

2. ALIASES HISTÓRICOS

Los nombres siguientes ya NO son contratos de gameplay activo:

    turnKey
    turnPhase
    turn / turnStartedAt
    *TurnKey
    *UsedTurn
    damagedThisTurn
    turnsRemaining / baseTurns
    summonedTurn / summonedPhase
    currentPlayer

Se leen/escriben únicamente en `web/js/core/runtime-contracts.js` como aliases de
compatibilidad para snapshots o clientes v239 y anteriores. En Firebase,
`currentPlayer` queda como sentinel wire=0 mientras dure esa compatibilidad.

3. MAPEO DE MIGRACIÓN

    turnKey                 -> combatWindowKey
    turnPhase               -> runtimeMode
    turn                    -> combatWindowIndex
    turnStartedAt           -> combatWindowStartedAt
    fooTurnKey              -> fooWindowKey
    fooUsedTurn             -> fooUsedWindow
    damagedThisTurn         -> damagedThisWindow
    turnsRemaining          -> cyclesRemaining
    baseTurns               -> baseCycles
    bleedTurnsRemaining     -> bleedCyclesRemaining
    veilCurseTurnsRemaining -> veilCurseCyclesRemaining
    summonedTurn            -> summonedWindowIndex
    summonedPhase           -> summonedRuntimeMode

4. CAMPOS *Turns QUE SE CONSERVAN DELIBERADAMENTE

Campos de contenido persistente como `poisonTurns`, `burnTurns`, `shieldTurns`,
`paralysisTurns`, `reviveTurns`, `dragonFrostTurns`, `electrocutionTurns` y similares
no son control de turno de jugador. Son nombres históricos de esquema de cartas/estados
que representan duración periódica. Se conservan para no romper mazos, cartas o estados
guardados. Su semántica actual es de ciclos/ticks del motor.

5. IDS DE UI/LAYOUT HISTÓRICOS

Selectores como `turnTimerHud`, `turnHonorHud` o claves de layout antiguas pueden
permanecer porque forman parte de calibraciones/JSON persistidos. No deben usarse para
introducir lógica de turnos nueva.

6. FIREBASE / PVP

El resultado online ya no se autoriza usando `currentPlayer`. El cliente que realiza el
commit terminal declara `resultCommitOwner`, y Firebase valida que ese rol corresponda
al UID autenticado de J1/J2. Los aliases legacy del runtime se generan solamente en la
frontera Firebase mediante `expandHallvallaLegacyRuntimePatch`.

7. REGLA PERMANENTE DE MANTENIMIENTO

- No agregar gameplay nuevo basado en turnKey/turnPhase/currentPlayer.
- No alternar jugadores mediante una ventana técnica.
- No exponer nombres técnicos del runtime en HUD/tutorial/logs de producción.
- Si se retira la compatibilidad con builds <= v239 en el futuro, eliminar los aliases
  únicamente desde `core/runtime-contracts.js` y Firebase Rules en una migración
  controlada.
